# BUILD

**🏗️ Idea to finished work: CONCEIVE designs; BRAID makes and checks.**

BUILD carries an idea from considered design into making, independent checking and supervision. CONCEIVE gives the design five separate contexts; BRAID gives execution three responsibilities: MAKER makes, CHECKER checks, SUPERVISOR supervises.

The handoff preserves your original purpose, constraints, material decisions, assumptions and observations that define success. If making exposes a material design problem, the relevant question and evidence return to design while unaffected work survives. A settled design can pass straight to BRAID.

## Start here

Read [INSTALL.md](INSTALL.md) to install the complete `build` folder in Codex and verify discovery. The operative entrypoint is [build/SKILL.md](build/SKILL.md). Keep its nested resources intact.

Before a full launch, try an explanation:

```text
Use BUILD to explain how you would approach this idea: [your idea]. Do not create chats, schedules or files yet.
```

When you are ready for the full journey, this named command requests **five communicating CONCEIVE design chats followed, when ready, by three BRAID execution chats, including one recurring SUPERVISOR check normally every ten minutes until completion**. Your narrower instructions still govern; add `Do not schedule unattended supervision` to exclude the recurring check.

```text
Create a BUILD called [name]: [the outcome you want designed and made].
```

State the intended user, important constraints and what a successful result lets you do. Include any budget, delivery location or reserved decision. A prepared brief is not an active participant; expect the actual collaboration mode and observed state before treating the launch as live.

## Choose a workflow

Use **BUILD** for design through delivery, **CONCEIVE** for design only, or **BRAID** for making and checking a settled objective. You can request CONCEIVE or BRAID directly. This package carries complete attributed snapshots of both workflows; an available current installation can be selected with its governing version recorded. Do not install nested snapshots as duplicate tool entries.

For commands and examples, read the [workflow guide](https://github.com/Stunspot/build/blob/main/docs/use.md). The [illustrative walkthrough](build/examples/walkthrough.md) shows a small teaching tool carried from design into making; it is not a recorded native collaboration trial.

## Know the host boundary

Codex is the targeted host for BUILD 0.1.0. The host supplies real contexts, tools, file access, communication, permissions and scheduling. Temporary subagents retain their actual lifecycle and capacity limits. If the host cannot provide a requested feature, BUILD should name the gap and continue only what it can support; it must not simulate completed coordination.

Multiple contexts and supervision consume the host's model allowance and may incur account charges. BUILD includes no model, quota or optional specialist skills. Give it a useful scope and budget; account controls govern enforceable usage limits. Share only appropriate context, and keep credentials out of briefs.

## Verify, recover and get help

Installation succeeds when the host reads the installed entrypoint and identifies all three workflows. Work completes when the requested artifact exists at its authorized delivery surface, matches the revision independently checked and has its material limits stated. A launch message or package check alone is not completion.

If interrupted, resume the existing BUILD record and recover its phase, revisions, actual collaborators, next actor and supervision schedule before creating replacements. See [recovery and support](https://github.com/Stunspot/build/blob/main/docs/recovery.md).
